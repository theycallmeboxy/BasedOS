#BasedOS user guide (GKD 350H Ultra)

BasedOS is a small operating system that lives on the 350H Ultra's internal storage (eMMC) and starts spruce from your SD card. Your spruce card stays a normal spruce card: you can move it between the 350H Ultra and your other spruce devices.

!

Status: early, pre-releases only. BasedOS is installed next to the stock firmware by basedos-setup (below), on the device itself. Read "Recovery" before you start.

#What you need

  • A GKD 350H Ultra on stock firmware ROCKNIX 20260613, build c8ed06c (other builds are refused: BasedOS runs on your device's own stock kernel, drivers and firmware, in place, and checks them).
  • To run setup, either a PC with SSH and Wi-Fi on stock, or a spare SD card for a setup card (no PC or network on the device; below).
  • An SD card you can erase, for the recovery card (recommended; setup says what size).
  • A spruce card (FAT32 or exFAT) with spruce for the 350H Ultra: an unofficial full build from the spruce fork's releases, or spruce plus the 350H Ultra kit (see spruce-on-gkd.md).

#Setup on the device (basedos-setup)

basedos-setup.sh runs on the 350H Ultra itself, under stock. There are two ways to run it: from a PC over SSH (here), or from a setup card with no PC (below); both offer the same choices.

Over SSH it downloads its release from GitHub. From a PC, in one go (press Enter at the password prompt: stock's root has none; the release page has the exact line for each release):

ssh -t root@<device> "curl -fsSL -o /tmp/basedos-setup.sh <release URL>/basedos-setup.sh && sh /tmp/basedos-setup.sh"

It checks stock's build and files first, states its requirements, asks everything, shows a numbered summary, asks you to type the confirmations (capitals don't matter), and only then downloads and writes. What it offers depends on what it finds on the device:

Before Install, Repair or Uninstall it recommends making a recovery card and offers to in the same run (the change happens only once the card is made and checked). Over SSH you type INSTALL, REPAIR or UNINSTALL to confirm you understand the built-in storage is modified, know the risks and have a backup. Setup installs the release it comes with: to go back to an older release, run that release's setup.

If setup stops part-way (Ctrl-C, the SSH connection drops), run it again. A card is simply made again. An install is finished: BasedOS's boot script goes in last, so until then stock still starts, and setup recognises the unfinished install and replaces it.

#Without a PC: the setup card

Each release also has basedos-setup-card-<release>.zip. Unpack it onto the root of a spare SD card (FAT32 or exFAT; not your spruce card, whose Roms folder stock doesn't read). It holds BasedOS's menu, roms/ports/BasedOS.sh, and the release in basedos-setup/. Power off, put the card in, power on into stock, and run Ports > BasedOS. Stock reads a card only at power-on: swapped while stock runs, it still shows the card that was in. With the setup card in, stock's Ports shows the card's own roms/ports (stock uses the card's roms folder, and makes its own system folders there), so BasedOS's menu from the card is the one there.

The entry copies the release into memory and checks it (on the screen, a file at a time), then runs the same setup with BasedOS's screens: Up/Down and A choose, B goes back to stock before anything is written, and the summary is confirmed by tapping A, B, X, Y in that order, as in BasedOS's maintenance menu. Stock's frontend is stopped while it runs. The checks and the recovery card's backup show how far they've got. While BasedOS is installed, the menu also has Disable BasedOS or Enable BasedOS, as below.

For a recovery card, setup releases the setup card first (it's unmounted, so it comes out clean): take it out and put in the card to erase, or use the setup card itself (setup has what it needs in memory). The screen shows the card in the slot, and A takes it. At the end it restarts or goes back to stock (after a recovery card: it powers off).

#BasedOS in stock's Ports

From stock, while BasedOS is installed, stock's Ports has BasedOS: BasedOS's menu, with its version, stock's build, the battery and whether BasedOS is on or disabled. It shows BasedOS's screens, as its maintenance menu does (stock's frontend stops while it's up, and starts again after), and Disable and Uninstall want A, B, X, Y tapped in that order:

  • Disable BasedOS, while BasedOS is on (in stock after "Boot Stock OS", or after setup): stock starts from then on, without a restart; BasedOS's files stay. The same as "Disable BasedOS" in BasedOS's maintenance menu.
  • Enable BasedOS, while it's disabled: BasedOS's boot script goes back and the device restarts into BasedOS.
  • Uninstall BasedOS: removes BasedOS, its settings and this Ports entry, and leaves stock as it was. To install it again: setup, from a PC or a setup card (Ports > BasedOS on the card offers Install).

(Stock's Ports shows only what's in it; this entry is what makes BasedOS appear there.)

To go back to stock: the maintenance menu (below, Everyday use), or from SSH basedos-boot stock-once, disable or uninstall (add --reboot); basedos-boot status says what boots next. install-dev.sh revert (from stock or BasedOS) still puts stock's boot script back and leaves BasedOS's files.

These are careful with the boot script, the one file that decides whether the device boots: each script is checked before it's written (a well-formed boot script, BasedOS's or stock's as expected; stock's against the known stock build) and read back after; everything a switch needs is in place first, so a failure leaves the device as it was; nothing is removed until stock's script is back.

Without a card, or with a card that has no frontend on it (a setup card, say), BasedOS waits for one and says so on screen; a card with a frontend put in then starts it. While it waits, the buttons the boot-key map uses work there too, held for a second: Select for maintenance mode, Start for stock once (or whatever /data/boot-keys.conf maps them to), without restarting first. The screen stays on while it waits, so a device left there runs its battery down.

#Wi-Fi and SSH

  • Wi-Fi is spruce's, as on its other devices: join, forget and switch it off from spruce's menu. The networks are saved on the card, so they go wherever the card goes. BasedOS only loads the Wi-Fi driver at boot.
  • BasedOS's own Wi-Fi is for maintenance mode, and for when the frontend keeps failing: then it joins the networks in /data/wpa_supplicant.conf on the eMMC. Each time it starts, it first adds any network stock has saved that it doesn't have yet (stock's own files are only read): to add a network, join it once in stock's Wi-Fi menu (start stock once), and maintenance mode knows it from then on. The file can also be edited over SSH.
  • SSH: with spruce's "Enable SSH" on, spruce's own SSH answers: user spruce, password happygaming. With it off there is no SSH. In maintenance mode, or when the frontend keeps failing, BasedOS's own SSH answers as root with no password. Use only on a network you trust.

#Updates

  • Each release on GitHub has its baseos-gkd350hultra-<version>.bosupd. BasedOS installs one only when you ask, in either of two ways:
    • spruce's firmware update app: it downloads the update (or finds one you put at the root of the card), asks you, and restarts; BasedOS installs it while starting, before spruce, and restarts once more into the new version. (The app's download only sees GitHub's latest full release, so while BasedOS has only pre-releases, download the .bosupd from the release page yourself and put it at the root of the card.)
    • The maintenance menu (Select held at power-on): Install update lists the .bosupd files on the card, older ones too (you're choosing by hand), and installs the one you pick. It asks for A, B, X, Y.

    A .bosupd that's only on the card is never installed by itself.

  • It's checked after it's written, and put in place while the device restarts. BasedOS keeps one copy of itself: if the new version doesn't start, the device starts stock after three tries, and setup, run from stock, repairs BasedOS (Repair puts its release back).
  • An update it won't install, when asked to, is renamed on the card, so neither BasedOS nor spruce's updater keeps offering it: .bosupd.skipped (not newer than the running release, or already installed once), .bosupd.refused (for another device or stock build, or a newer initrd), .bosupd.failed (it didn't verify). Rename one back to .bosupd to have it looked at again.
  • An update holds only BasedOS's own files, never your device's stock firmware (BasedOS uses stock's kernel, its modules, the GPU drivers and the firmware in place). Each BasedOS release is made for one stock firmware build; an update for another one is refused. To see what an update would do, from SSH: basedos-update status.
  • An update doesn't carry BasedOS's boot files either: the boot script and the initrd, which put the update in place and count failed starts, so a bad one would stop every start. They come with setup; a change needs a developer update (tools/dev/update-basedos.sh) for now. An update made for a newer initrd than the device has is refused (.bosupd.refused).

#Safeguards

  • Boot counter: if BasedOS fails to start three times in a row, the device starts stock, and keeps starting stock until setup's Repair (or deleting boot-attempts in BasedOS's data folder) resets it. A start that gets as far as BasedOS's own start-up counts as a good one, even when its data partition needs a check it can't do by itself.
  • Bad boot files: if BasedOS's initrd is missing or damaged, or its whole folder is gone, the boot script boots stock (with its folder deleted: tested 2026-11-21). Updates never change the boot files, so after a bad update stock still starts, and setup can repair BasedOS from there.
  • Stock changed: if stock isn't the build BasedOS was made for (reflashed, say), BasedOS doesn't start and stock boots. Enable BasedOS in stock's Ports > BasedOS checks this first and says so, instead of enabling a BasedOS that wouldn't start.
  • Frontend crash loop: if spruce exits within 15 s five times in a row, BasedOS stops restarting it and shows a message, instead of looping. Wi-Fi and SSH come up so it can be looked at, and Select or Start held for a second there still go to maintenance mode or stock.
  • Card checks: a card left dirty by a power cut is checked (fsck) once before use.
  • Clean shutdown: BasedOS's own power-off and restart (the volume-key combo, SSH) turn off a swap file on the card and release anything loop-mounted from it first, as spruce's own power-off does, so the card is left clean.

#Recovery

If anything goes wrong, see recovery.md. In short, from gentlest to strongest:

  1. Recovery card (basedos-setup's "Make a recovery SD card"): power on with it in; it checks its backup, and when you tap A, B, X, Y in that order it puts the built-in storage back as it was when the card was made, then checks it. Tapping power powers off without writing. No PC needed. A restore from a recovery card was verified byte for byte on a unit (2026-11-20, with the earlier hold-A screen), and one brought a unit back after a boot script hung (2026-11-21).
  2. USB disk mode: hold Menu + Home and power on; the whole eMMC appears on your PC.
  3. Maskrom: hold Volume Down and power on; RKDevTool on a PC can rewrite the whole eMMC (tested, including a full restore).

Every SD card, the recovery card included, needs the device's own bootloader (at the start of the built-in storage) to start: the chip never starts one from a card (tested). If the bootloader itself is gone, only maskrom and a PC bring the device back; the recovery card carries what that needs (its maskrom/ folder: Rockchip's USB loader and the steps, and the backup's own copy of the bootloader).

#Logs

  • BasedOS: /data/basedos.log on the eMMC (basedos-data/basedos.log seen from stock), about the last 256 KB; the part before is in basedos.log.1.
  • spruce: Saves/spruce/spruce.log and pyui.log on the card.
  • Stock's Ports > BasedOS: Uninstall logs to basedos-uninstall.log on stock's data partition (/storage), which it leaves there; Disable logs to basedos-data/basedos.log. Setup from a setup card logs to the journal (journalctl -u basedos-stock).

#For developers: installing a build

Setup (above) is the way to install. To install a build of your own instead:

  1. Prepare your stock files from a backup of your eMMC (recovery.md): python tools/prepare_stock.py <backup>/mmcblk0.img prepared. The build makes BasedOS's links into stock's files against them; nothing of stock's goes into BasedOS.
  2. In WSL: build (tools/wsl/build.sh; it unpacks your stock image the first time). It writes out/: the system layer (rootfs.squashfs), the initrd, BasedOS's boot script, the recovery card's files and an update payload (.bosupd).
  3. With the 350H Ultra running stock and reachable over SSH, copy out/ to /tmp on the device and run tools/install-dev.sh /tmp/<dir> there. It adds BasedOS's files to the boot partition (the system layer, the initrd), puts BasedOS's boot script in place of stock's (kept), copies your Wi-Fi network and SSH keys, and leaves stock's own files untouched.
  4. Reboot. BasedOS starts, then spruce from the card.
